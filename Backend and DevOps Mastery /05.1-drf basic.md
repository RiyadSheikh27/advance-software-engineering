## 1. CORE DRF BUILDING BLOCKS

| Component | Purpose |
|---|---|
| `Serializer` / `ModelSerializer` | Convert QuerySet/Model ↔ JSON, validate input |
| `APIView` | Base class-based view, manual control |
| `GenericAPIView` + Mixins | Reusable CRUD building blocks |
| `ViewSet` / `ModelViewSet` | Groups related views (list/create/retrieve/update/delete) into one class |
| `Router` | Auto-generates URLs for ViewSets |
| `Parser` | Reads incoming request body (JSON, MultiPart, FormData) |
| `Renderer` | Formats outgoing response (JSON, Browsable API) |
| `Authentication` classes | Identify **who** the user is |
| `Permission` classes | Decide **what** they can do |
| `Throttle` classes | Limit **how often** they can call |
| `Pagination` classes | Slice large querysets |
| `Filter backends` | Query param based filtering |

## 2. SERIALIZERS DEEP TECHNIQUES

### 2.1 ModelSerializer vs Serializer
- **ModelSerializer**: auto-generates fields from model — use for standard CRUD.
- **Serializer**: manual field declaration — use for non-model input (e.g. login payload, complex aggregated output).

### 2.2 `SerializerMethodField` — computed/read-only fields
```python
class OrderSerializer(serializers.ModelSerializer):
    total_with_tax = serializers.SerializerMethodField()

    def get_total_with_tax(self, obj):
        return obj.total * Decimal("1.05")

    class Meta:
        model = Order
        fields = ["id", "total", "total_with_tax"]
```
**Why**: adds derived data without touching DB schema. **Caution**: runs in Python per-object — avoid heavy queries inside (causes N+1).

### 2.3 Nested Serializers vs `PrimaryKeyRelatedField` vs `SlugRelatedField`
- Nested serializer → full object embedded (heavier payload, more queries).
- `PrimaryKeyRelatedField` → just the ID (fastest, least payload) — **preferred for write & lightweight read**.
- `SlugRelatedField` → human-readable reference (e.g. username) instead of ID.
- `StringRelatedField` → calls `__str__()`, read-only, avoid in hot paths (extra query per row if not prefetched).

### 2.4 `to_representation` / `to_internal_value` override
Use to reshape output/input beyond declarative fields (e.g. flatten nested data, rename keys for legacy clients).

### 2.5 `validate_<field>` and `validate()`
Field-level validation and cross-field validation (e.g. `start_date < end_date`).

### 2.6 Writable Nested Serializers
DRF doesn't support nested create/update out of the box — override `create()`/`update()` manually, wrap in `transaction.atomic()`.

### 2.7 `source=`, `read_only`, `write_only`
- `source="user.email"` → traverse relations without extra serializer.
- `write_only=True` → passwords, secrets never returned in response.

### 2.8 `many=True` and bulk serialization
For list serialization, always pair with `select_related`/`prefetch_related` on the queryset feeding it — serializer doesn't know about DB efficiency, the **view** controls that.

### 2.9 Dynamic fields serializer (senior trick)
```python
class DynamicFieldsModelSerializer(serializers.ModelSerializer):
    def __init__(self, *args, fields=None, **kwargs):
        super().__init__(*args, **kwargs)
        if fields is not None:
            allowed = set(fields)
            for field_name in set(self.fields) - allowed:
                self.fields.pop(field_name)
```
**Why**: lets API consumers request only needed fields (`?fields=id,name`) → smaller payload, faster response. Similar idea to GraphQL but in REST.

## 3. VIEWS: APIView vs GenericAPIView vs ViewSets

```python
# APIView — full manual control, best for custom logic (e.g. payment webhook)
class ChargeCardAPIView(APIView):
    permission_classes = [IsAuthenticated]

    def post(self, request):
        serializer = ChargeSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        result = payment_service.charge(**serializer.validated_data)
        return Response(result, status=status.HTTP_201_CREATED)
```

```python
# GenericAPIView + mixins — reusable, less boilerplate
class ProductListCreateView(generics.ListCreateAPIView):
    queryset = Product.objects.select_related("category")
    serializer_class = ProductSerializer
    filter_backends = [DjangoFilterBackend]
    filterset_fields = ["category"]
```

```python
# ViewSet — grouped CRUD + custom actions, routed automatically
class OrderViewSet(viewsets.ModelViewSet):
    queryset = Order.objects.select_related("user").prefetch_related("items")
    serializer_class = OrderSerializer

    @action(detail=True, methods=["post"])
    def cancel(self, request, pk=None):
        order = self.get_object()
        order.cancel()
        return Response({"status": "cancelled"})
```

**When to use which:**
- `APIView`: one-off, non-CRUD endpoints (webhooks, auth, custom business action).
- `Generic + Mixins`: standard REST resource, but you want to override 1-2 methods.
- `ViewSet + Router`: full CRUD resource with predictable URL patterns — best for large APIs, keeps urls.py clean.

## 4. ROUTERS & URL DESIGN
```python
router = DefaultRouter()
router.register("orders", OrderViewSet, basename="order")
urlpatterns = [path("api/v1/", include(router.urls))]
```
- **DefaultRouter**: adds browsable API root view.
- **SimpleRouter**: no root view — for production APIs where browsable root isn't needed.
- **API Versioning**: prefix (`/api/v1/`), header-based (`Accept: application/vnd.myapp.v2+json`), or DRF's `URLPathVersioning`/`NamespaceVersioning`. **Why**: avoid breaking old clients; senior devs never mutate a live contract, they version it.

## 5. AUTHENTICATION

| Method | Use Case |
|---|---|
| `SessionAuthentication` | Browser-based, same-domain frontend (uses CSRF) |
| `TokenAuthentication` (DRF built-in) | Simple, but token doesn't expire, single token/user — rarely used in production |
| `JWT` (SimpleJWT) | Stateless, scalable, works cross-domain/mobile — **industry standard** |
| `OAuth2` (django-oauth-toolkit) | Third-party app authorization, "Login with X" |
| `API Key auth` | Server-to-server / partner integrations |
| `mTLS` | High-security service-to-service (fintech, banking) |

### JWT Example (SimpleJWT)
```python
# settings.py
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": (
        "rest_framework_simplejwt.authentication.JWTAuthentication",
    )
}
```
- **Access token**: short-lived (5–15 min) — sent on every request.
- **Refresh token**: long-lived, stored securely (HttpOnly cookie), used to mint new access tokens.
- **Why short-lived access tokens**: limits blast radius if leaked.
- **Token rotation + blacklist**: rotate refresh token on every use, blacklist old one → prevents replay attacks.

### Custom Authentication class
```python
class ApiKeyAuthentication(BaseAuthentication):
    def authenticate(self, request):
        key = request.headers.get("X-API-KEY")
        if not key:
            return None
        try:
            client = ApiClient.objects.get(key=key, is_active=True)
        except ApiClient.DoesNotExist:
            raise AuthenticationFailed("Invalid API key")
        return (client, None)
```
**Where used**: webhook receivers, partner/B2B integrations, internal microservice calls.

## 6. AUTHORIZATION / PERMISSIONS

```python
class IsOwnerOrReadOnly(BasePermission):
    def has_object_permission(self, request, view, obj):
        if request.method in SAFE_METHODS:
            return True
        return obj.owner == request.user
```
- `IsAuthenticated`, `IsAdminUser`, `AllowAny`, `DjangoModelPermissions` — built-ins.
- **Object-level permissions** (`has_object_permission`) vs **view-level** (`has_permission`) — object-level runs only after `get_object()`, costs a query, so combine wisely.
- **RBAC (Role-Based Access Control)**: groups + permissions, or custom `Role` model with `FK` to user for fine-grained control.
- **ABAC (Attribute-Based Access Control)**: permission decided by resource attributes (department, tenant_id) — common in multi-tenant SaaS/fintech.
- **Scopes** (OAuth2): permission tied to token scope (`read:transactions`, `write:transactions`).

## 7. SECURITY HARDENING (OWASP-aligned)

| Threat | Technique |
|---|---|
| SQL Injection | Django ORM parameterizes queries by default — never use raw SQL string formatting; use `params=[]` if raw SQL needed |
| XSS | DRF JSON renderer escapes by default; sanitize any HTML-rendered content |
| CSRF | Required for `SessionAuthentication`; not needed for token/JWT (stateless) |
| Mass assignment | Explicitly whitelist serializer `fields`, never `fields = "__all__"` blindly on write-enabled serializers |
| Broken auth | Enforce strong password hashing (Argon2/bcrypt via Django's `PASSWORD_HASHERS`), MFA for sensitive ops |
| Secrets in code | Use env vars / `django-environ` / AWS Secrets Manager / Vault — never commit `.env` |
| IDOR (Insecure Direct Object Reference) | Always filter queryset by `request.user`, never trust client-supplied IDs blindly |
| Rate abuse | Throttling (see §17) |
| Data in transit | HTTPS everywhere, HSTS header |
| Data at rest | Encrypt sensitive fields (`django-cryptography`, or field-level AES) — especially PII/PCI data |
| Clickjacking | `X-Frame-Options: DENY` (Django middleware default) |
| CORS misconfig | `django-cors-headers`, whitelist exact origins, never `CORS_ALLOW_ALL_ORIGINS=True` in prod |
| Dependency vulns | `pip-audit` / `safety` in CI pipeline |
| Sensitive data exposure | Never log passwords/card numbers/tokens; mask in logs (`**** **** **** 1234`) |

### Example: preventing IDOR
```python
def get_queryset(self):
    return Transaction.objects.filter(user=self.request.user)  # never Transaction.objects.all()
```

### Security headers via middleware
```python
SECURE_SSL_REDIRECT = True
SECURE_HSTS_SECONDS = 31536000
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
SECURE_CONTENT_TYPE_NOSNIFF = True
```

## 8. DATABASE & ORM PERFORMANCE (N+1 AND BEYOND)

### 8.1 The N+1 Problem
**What**: 1 query to fetch list + N queries (one per row) to fetch related objects.
```python
# BAD — N+1
orders = Order.objects.all()
for o in orders:
    print(o.user.email)     # hits DB every loop
```
```python
# GOOD — select_related (SQL JOIN, for FK / OneToOne)
orders = Order.objects.select_related("user")

# GOOD — prefetch_related (separate query + Python join, for M2M / reverse FK)
orders = Order.objects.prefetch_related("items")

# Combine both
orders = Order.objects.select_related("user").prefetch_related("items__product")
```
**Why select_related vs prefetch_related**: `select_related` = SQL JOIN (single query, use for FK/O2O — small predictable joins). `prefetch_related` = separate query then joined in Python (use for reverse FK/M2M — avoids cartesian product blow-up from JOINs on multi-valued relations).

### 8.2 `Prefetch` object for fine control
```python
from django.db.models import Prefetch
Order.objects.prefetch_related(
    Prefetch("items", queryset=OrderItem.objects.select_related("product"))
)
```

### 8.3 `only()` / `defer()`
Fetch only needed columns → reduces I/O and memory.
```python
User.objects.only("id", "email")
```

### 8.4 `values()` / `values_list()`
Skip full model instantiation when you just need raw data/dicts — faster serialization for read-heavy dashboards.

### 8.5 Query annotation instead of Python loop
```python
Order.objects.annotate(item_count=Count("items"))   # DB does the counting, not Python
```

### 8.6 Bulk operations
```python
Model.objects.bulk_create(objs, batch_size=1000)
Model.objects.bulk_update(objs, ["field1"], batch_size=1000)
```
**Why**: single/few round-trips instead of N inserts/updates — critical for imports/batch jobs.

### 8.7 `exists()` / `count()` instead of `len(queryset)`
Avoid loading full queryset into memory just to check existence or size.

### 8.8 Database Indexing
```python
class Meta:
    indexes = [models.Index(fields=["status", "created_at"])]
```
- Index columns used in `filter()`, `order_by()`, and JOIN conditions.
- **Composite index** order matters — most selective / most-queried field first.
- Beware: indexes slow down writes — don't over-index write-heavy tables (e.g. ledger tables).

### 8.9 `select_for_update()` — row locking
```python
with transaction.atomic():
    account = Account.objects.select_for_update().get(id=account_id)
    account.balance -= amount
    account.save()
```
**Why**: prevents race conditions on concurrent writes (classic **double-spend bug** in wallets/fintech). Locks the row until transaction commits.

### 8.10 `transaction.atomic()`
Wraps multiple DB writes into one all-or-nothing unit — essential for financial operations (debit+credit must both succeed or both fail).

### 8.11 Connection Pooling
- Django opens a new DB connection per request by default (with `CONN_MAX_AGE` for persistent connections).
- Use **PgBouncer** (Postgres) in front of DB for connection pooling at scale — DB has limited max connections, app servers scale horizontally, pooler mediates.
- `CONN_MAX_AGE = 60` in settings enables persistent connections (Django-level pooling).

### 8.12 Read Replicas
- Route heavy `SELECT` (reports, analytics) to read replica DB, writes go to primary.
```python
DATABASE_ROUTERS = ["myapp.routers.ReadReplicaRouter"]
```
**Why**: offloads read traffic from primary, improves write throughput and read scalability.

### 8.13 Database-level constraints over app-level only
`UniqueConstraint`, `CheckConstraint` — enforce data integrity even if application code has bugs.

### 8.14 Query debugging tools
`django-debug-toolbar` (dev), `django-silk` (profiling), `EXPLAIN ANALYZE` on slow queries, `nplusone` package to auto-detect N+1 in tests.

### 8.15 Pagination at DB level (don't SELECT everything)
Always paginate — `LIMIT/OFFSET` or better, **cursor pagination** for large tables (see §9).

## 9. PAGINATION, FILTERING, SEARCH, ORDERING

```python
REST_FRAMEWORK = {
    "DEFAULT_PAGINATION_CLASS": "rest_framework.pagination.CursorPagination",
    "PAGE_SIZE": 20,
}
```
- **PageNumberPagination**: simple `?page=2` — but `OFFSET` gets slow on large tables (DB still scans skipped rows).
- **LimitOffsetPagination**: flexible client-controlled, same offset cost issue at scale.
- **CursorPagination**: uses an opaque cursor (based on ordered field, e.g. `id` or `created_at`) — **O(1) style performance regardless of page depth**, best for infinite-scroll feeds and large tables. Industry standard at scale (Twitter/Facebook-style feeds).

### Filtering
```python
class ProductFilter(django_filters.FilterSet):
    min_price = django_filters.NumberFilter(field_name="price", lookup_expr="gte")
    class Meta:
        model = Product
        fields = ["category", "min_price"]
```
`django-filter` for structured filters, `SearchFilter` for `?search=` full-text-ish, `OrderingFilter` for `?ordering=-created_at`.

## 10. CACHING WITH REDIS

### 10.1 Why Redis
In-memory key-value store — sub-millisecond reads, used for caching, session store, rate-limit counters, Celery broker/result backend, pub/sub, distributed locks.

### 10.2 View-level caching
```python
from django.utils.decorators import method_decorator
from django.views.decorators.cache import cache_page

class PopularProductsView(APIView):
    @method_decorator(cache_page(60 * 15))   # 15 min
    def get(self, request):
        ...
```

### 10.3 Low-level cache API (fine-grained control)
```python
from django.core.cache import cache

def get_dashboard_data(user_id):
    key = f"dashboard:{user_id}"
    data = cache.get(key)
    if data is None:
        data = build_expensive_dashboard(user_id)
        cache.set(key, data, timeout=300)
    return data
```

### 10.4 Caching Strategies
| Strategy | How it works | Use case |
|---|---|---|
| Cache-aside (lazy loading) | App checks cache, on miss loads from DB & populates cache | Most common, general reads |
| Write-through | Write to cache and DB simultaneously | Data must always be fresh in cache |
| Write-behind | Write to cache first, async flush to DB | High write throughput tolerant of eventual consistency |
| TTL-based expiry | Auto-expire stale data | Simplicity, avoids manual invalidation |

### 10.5 Cache Invalidation
- **Explicit invalidation**: delete key on model save via signals.
```python
@receiver(post_save, sender=Product)
def clear_product_cache(sender, instance, **kwargs):
    cache.delete(f"product:{instance.id}")
```
- **Versioned keys** (`cache.set(f"product:v2:{id}", ...)`) — bump version to invalidate everything at once without scanning keys.
- "There are only two hard things in CS: cache invalidation and naming things" — be deliberate.

### 10.6 Redis for Sessions
```python
SESSION_ENGINE = "django.contrib.sessions.backends.cache"
SESSION_CACHE_ALIAS = "default"
```
Faster than DB-backed sessions, avoids hitting Postgres for every authenticated request.

### 10.7 Redis Distributed Lock
```python
lock = redis_client.lock("charge_lock:%s" % order_id, timeout=10)
if lock.acquire(blocking=True, blocking_timeout=5):
    try:
        process_payment(order_id)
    finally:
        lock.release()
```
**Why**: prevents duplicate processing across multiple app server instances (e.g. double webhook delivery).

### 10.8 Rate limiting with Redis (sliding window / token bucket)
Used to implement custom throttles beyond DRF's default (see §17).

## 11. CELERY — ASYNC TASKS & SCHEDULING

### 11.1 Why
Offload slow/non-critical work (emails, PDF generation, report building, ledger reconciliation, webhook retries) out of the request-response cycle → **fast API response**.

```python
# tasks.py
@shared_task(bind=True, max_retries=3, default_retry_delay=10)
def send_receipt_email(self, order_id):
    try:
        order = Order.objects.get(id=order_id)
        email_service.send(order)
    except SomeTransientError as exc:
        raise self.retry(exc=exc)
```
```python
# view
class OrderCreateView(APIView):
    def post(self, request):
        order = create_order(request.data)
        send_receipt_email.delay(order.id)   # fire-and-forget, non-blocking
        return Response(OrderSerializer(order).data, status=201)
```

### 11.2 Key concepts
- **Broker** (Redis/RabbitMQ): queues tasks.
- **Result backend** (Redis): stores task results/status.
- **Worker**: separate process(es) consuming the queue.
- **`.delay()`** vs **`.apply_async()`**: latter allows `countdown`, `eta`, `queue=`, `priority`.
- **Idempotent tasks**: tasks may be delivered more than once (at-least-once delivery) — design tasks to be safely re-runnable (check state before acting).
- **Celery Beat**: cron-like periodic tasks (`crontab(hour=0, minute=0)`) — daily settlement jobs, cleanup jobs.
- **Task routing / queues**: separate queues per priority (`payments`, `emails`, `reports`) so critical tasks aren't stuck behind bulk ones.
- **Retries with exponential backoff**: avoid hammering a failing downstream service.
- **Chains / Groups / Chords**: compose multi-step workflows (`chain(task1.s(), task2.s())`).

### 11.3 When NOT to use Celery
Don't use for things needing an immediate synchronous response to the user (e.g. returning a computed price) — use it only for **side effects**.

## 12. KAFKA — EVENT STREAMING

### 12.1 Why Kafka over Celery for certain cases
Kafka = distributed **event log**, built for high-throughput, replayable, multi-consumer event streaming — not just a task queue. Used when **multiple independent services** need to react to the same event (event-driven architecture), and you need durability/replay/ordering guarantees Celery doesn't provide.

| | Celery | Kafka |
|---|---|---|
| Purpose | Task execution (RPC-style async jobs) | Event streaming / pub-sub log |
| Consumers | Usually one worker pool consumes a task once | Multiple consumer groups can independently replay the same stream |
| Durability | Task usually removed after processing | Events retained for a configurable period, replayable |
| Use case | Send email, generate PDF | "OrderPlaced" event triggers inventory service, billing service, notification service independently |

### 12.2 Basic Producer/Consumer (kafka-python / confluent-kafka)
```python
# Producer — inside a service after DB commit
producer.send("order.created", value=json.dumps({
    "order_id": order.id, "user_id": order.user_id, "amount": str(order.total)
}).encode())
```
```python
# Consumer — separate service/process
for message in consumer:
    event = json.loads(message.value)
    handle_order_created(event)
```

### 12.3 Key Kafka Concepts
- **Topic**: named event stream (`order.created`).
- **Partition**: topic split for parallelism; ordering guaranteed **within** a partition only.
- **Consumer Group**: set of consumers sharing the load of a topic — each partition consumed by only one member of the group.
- **Offset**: consumer's position in the log — enables replay/resume.
- **At-least-once delivery**: consumers must be idempotent (dedupe using event id).

### 12.4 Transactional Outbox Pattern (critical for fintech/microservices)
**Problem**: writing to DB and publishing to Kafka aren't atomic — you can crash between the two (dual-write problem).
**Solution**: write the event to an `Outbox` table **in the same DB transaction** as the business write; a separate relay process/CDC (e.g. Debezium) reads the outbox and publishes to Kafka reliably.
```python
with transaction.atomic():
    order = Order.objects.create(...)
    Outbox.objects.create(event_type="order.created", payload=json.dumps(...))
```

## 13. MICROSERVICES PATTERNS

| Pattern | What / Why |
|---|---|
| **API Gateway** | Single entry point, handles auth/rate-limit/routing to internal services (Kong, AWS API Gateway) — clients don't talk to services directly |
| **Service Discovery** | Services register themselves (Consul, Eureka, or k8s DNS) so others can find them dynamically instead of hardcoded IPs |
| **Circuit Breaker** | Stop calling a failing downstream service for a cooldown period to avoid cascading failure (`pybreaker`) |
| **Retry with backoff + jitter** | Resilient inter-service calls without thundering herd |
| **Saga Pattern** | Manage distributed transactions across services via a sequence of local transactions + compensating actions (since no distributed 2PC) — e.g. Order service reserves stock → Payment service charges → on failure, compensating "release stock" event |
| **Idempotency Keys** | Client sends unique key per operation; server dedupes retries — essential for payment APIs |
| **Event-Driven Architecture** | Services communicate via events (Kafka) instead of direct sync calls → loose coupling |
| **CQRS** | Separate read model from write model — write optimized for consistency, read optimized/denormalized for speed (common in high-read fintech dashboards) |
| **Database per service** | Each microservice owns its own DB — no shared DB across services, communicate via APIs/events only |
| **Sync (REST/gRPC) vs Async (Kafka/RabbitMQ) communication** | Sync when immediate response required; async for decoupled, eventual-consistency workflows |
| **gRPC** | Binary protocol (protobuf), much faster than REST/JSON for internal service-to-service calls — use for internal microservice mesh, REST/JSON for public-facing API |
| **Health checks** | `/healthz`, `/readyz` endpoints for orchestrators (k8s) to know if service is alive/ready |
| **Sidecar pattern** | Service mesh (Istio/Linkerd) handles retries, mTLS, observability outside app code |
| **Distributed Tracing** | Trace a request across multiple services (OpenTelemetry, Jaeger) using a correlation/trace ID passed through headers |

### Idempotency key example (DRF)
```python
class ChargeAPIView(APIView):
    def post(self, request):
        idem_key = request.headers.get("Idempotency-Key")
        cached = cache.get(f"idem:{idem_key}")
        if cached:
            return Response(cached, status=200)  # return same result, don't double-charge
        result = payment_service.charge(...)
        cache.set(f"idem:{idem_key}", result, timeout=86400)
        return Response(result, status=201)
```

## 14. FINTECH-SPECIFIC ENGINEERING

- **Use `Decimal`, never `float`, for money.** Float rounding errors are unacceptable in ledgers.
```python
from decimal import Decimal
amount = Decimal("19.99")
```
- **Double-entry ledger design**: every transaction records a debit and a credit entry (never just mutate a `balance` field directly) — gives full auditability and self-verifying books (sum of all entries = 0).
- **Immutable transaction records**: never `UPDATE`/`DELETE` a financial record — append corrections as new entries (append-only ledger).
- **Idempotency keys** on every mutating financial endpoint (charges, transfers) — network retries must not double-charge.
- **`select_for_update()` + `transaction.atomic()`** for balance updates — prevents race conditions/double-spend.
- **Webhook signature verification**: verify HMAC signature (e.g. Stripe-style `X-Signature` header) before trusting any incoming webhook payload.
```python
expected = hmac.new(secret.encode(), payload, hashlib.sha256).hexdigest()
if not hmac.compare_digest(expected, received_signature):
    raise PermissionDenied("Invalid signature")
```
- **Audit logging**: log who did what, when, from where, on every sensitive mutation — required for compliance (SOC2, PCI-DSS).
- **PCI-DSS basics**: never store raw card numbers/CVV — use a tokenization provider (Stripe/Braintree vault), only store tokens.
- **Reconciliation jobs**: scheduled (Celery Beat) jobs that compare internal ledger vs external payment processor records, flag mismatches.
- **Currency handling**: store amounts as integers in smallest unit (cents) OR `Decimal` with fixed precision — avoid floating point entirely; store currency code alongside amount.
- **Rate limiting stricter on financial endpoints** than regular endpoints.
- **Dual control / maker-checker pattern**: sensitive actions (large transfers, refunds) require a second approver.
- **Compliance**: KYC/AML flows, transaction monitoring for suspicious activity (rule-based or ML-based flags).

## 15. API PERFORMANCE & FAST RESPONSE TECHNIQUES

1. **Move slow work off the request cycle** → Celery async tasks (§11).
2. **select_related/prefetch_related** everywhere querysets feed serializers (§8).
3. **Cache expensive/read-heavy responses** in Redis (§10).
4. **Pagination always** — never return unbounded lists.
5. **`only()`/`values()`** to cut unneeded DB columns.
6. **Database indexing** on filter/order columns.
7. **Avoid serializer `SerializerMethodField` triggering queries per object** — precompute via `annotate()` instead.
8. **Use `gunicorn`/`uvicorn` with multiple workers** (`workers = 2 * CPU + 1`), and `--threads` for I/O-bound apps.
9. **Async views** (`async def get(self, request)`, Django 4.1+ supports async ORM calls) for I/O-bound endpoints (e.g. calling external APIs) — frees worker thread while waiting.
10. **Connection pooling** (PgBouncer) to avoid DB connection exhaustion under load.
11. **CDN** for static/media assets — offload from app servers.
12. **Gzip/Brotli compression** on responses (`django.middleware.gzip.GZipMiddleware`) — smaller payload, faster transfer.
13. **Database query result caching** for expensive aggregations.
14. **Horizontal scaling + load balancer** (Nginx/ALB) — stateless app servers behind LB, session state in Redis not local memory.
15. **Read replicas** to offload read traffic.
16. **Avoid N+1 in loops calling external APIs too** — batch external calls where possible.
17. **Lazy-load large fields** — e.g. don't return huge blobs in list endpoint, only in detail endpoint.
18. **Use `EXPLAIN ANALYZE`** to find slow queries in staging before they hit prod.
19. **APM tooling** (New Relic / Datadog / Sentry Performance) to catch regressions.

## 16. FASTEST DATA TRANSFER TECHNIQUES

| Technique | Why |
|---|---|
| **JSON (standard)** | Universal, human-readable — default for public REST APIs |
| **MessagePack / Protocol Buffers (protobuf)** | Binary, smaller & faster to (de)serialize — used for internal service-to-service (gRPC uses protobuf) |
| **gRPC over HTTP/2** | Multiplexed streams, binary, much lower latency than REST/JSON — internal microservices |
| **Gzip/Brotli compression** | Reduces payload size over the wire, cheap CPU cost for big bandwidth win |
| **Field selection / sparse fieldsets** (`?fields=id,name`) | Send only what client needs — smaller payload |
| **Cursor pagination** | Avoids huge payloads and expensive OFFSET scans (§9) |
| **HTTP/2 or HTTP/3 (QUIC)** | Multiplexing, header compression, lower latency vs HTTP/1.1 |
| **Streaming responses** (`StreamingHttpResponse`) | For huge exports (CSV/large reports) — don't build entire payload in memory |
| **`bulk_create`/`bulk_update`** | Fewest DB round-trips for bulk write operations |
| **ETags / conditional requests** (`If-None-Match`) | Client skips re-downloading unchanged data → `304 Not Modified` |
| **WebSockets (Django Channels)** | For real-time bidirectional data (chat, live price feeds) instead of polling REST repeatedly |

### Streaming large exports example
```python
class ExportCSVView(APIView):
    def get(self, request):
        def row_generator():
            yield "id,amount\n"
            for row in Transaction.objects.iterator(chunk_size=2000):
                yield f"{row.id},{row.amount}\n"
        return StreamingHttpResponse(row_generator(), content_type="text/csv")
```
`.iterator(chunk_size=...)` avoids loading the entire queryset into memory — critical for large exports.

## 17. RATE LIMITING & THROTTLING

```python
class BurstRateThrottle(UserRateThrottle):
    scope = "burst"

REST_FRAMEWORK = {
    "DEFAULT_THROTTLE_CLASSES": ["rest_framework.throttling.UserRateThrottle"],
    "DEFAULT_THROTTLE_RATES": {"user": "100/min", "burst": "10/sec", "anon": "20/min"},
}
```
- **AnonRateThrottle**: per-IP for unauthenticated users.
- **UserRateThrottle**: per authenticated user.
- **ScopedRateThrottle**: different limits per view (`throttle_scope = "uploads"`).
- **Custom Redis-based sliding window/token bucket**: for precise, distributed rate limiting across multiple app servers (DRF's default cache-based throttle works but token bucket in Redis is more accurate at scale).
- **Why**: prevent abuse, brute-force attacks, protect downstream services (esp. payment gateways) from overload, enforce fair usage/tiered plans.

## 18. ERROR HANDLING & API CONTRACTS

### Consistent error response shape
```python
def custom_exception_handler(exc, context):
    response = exception_handler(exc, context)
    if response is not None:
        response.data = {
            "error": {
                "code": response.status_code,
                "message": str(exc),
                "details": response.data,
            }
        }
    return response
```
```python
REST_FRAMEWORK = {"EXCEPTION_HANDLER": "myapp.utils.custom_exception_handler"}
```
- **Use proper HTTP status codes**: 400 (validation), 401 (unauthenticated), 403 (forbidden), 404, 409 (conflict, e.g. duplicate), 422 (semantic error), 429 (rate limited), 500.
- **Never leak stack traces / internal errors to client** in production (`DEBUG=False`).
- **Structured error codes** (machine-readable `"INSUFFICIENT_FUNDS"`) alongside human message — lets frontend/clients branch logic reliably.
- **API versioning + deprecation headers** (`Sunset` header) when retiring endpoints.

## 19. CODE ARCHITECTURE (SENIOR-LEVEL STRUCTURE)

### 19.1 Service Layer Pattern
Keep views thin — business logic lives in a service layer, not in the serializer or view.
```python
# services/order_service.py
def place_order(user, cart_items):
    with transaction.atomic():
        order = Order.objects.create(user=user)
        OrderItem.objects.bulk_create([...])
        inventory_service.reserve_stock(cart_items)
        send_receipt_email.delay(order.id)
    return order

# views.py
class OrderCreateView(APIView):
    def post(self, request):
        serializer = PlaceOrderSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        order = order_service.place_order(request.user, serializer.validated_data["items"])
        return Response(OrderSerializer(order).data, status=201)
```
**Why**: testable business logic independent of HTTP layer, reusable across REST/Celery task/management command/GraphQL.

### 19.2 Repository Pattern (optional, for complex domains)
Abstract DB access behind a repository interface — makes swapping data sources or heavy mocking in tests easier. Often skipped in Django (ORM itself is the abstraction) but used in DDD-heavy fintech codebases.

### 19.3 SOLID in Django context
- **S**ingle Responsibility: serializer validates/shapes data, service handles business logic, view handles HTTP only.
- **O**pen/Closed: use permission classes/strategy pattern instead of giant if/else in views.
- **L**iskov: custom permission/authentication classes should honor base class contracts.
- **I**nterface Segregation: small, focused serializers/mixins instead of one giant serializer.
- **D**ependency Inversion: services depend on abstractions (e.g. a `PaymentGateway` interface) not concrete Stripe SDK calls directly — swap providers without rewriting business logic.

### 19.4 Fat models / Thin views / Thinner serializers
Common Django idiom — but for larger systems, **service layer > fat models**, since fat models get bloated and hard to test in isolation.

### 19.5 Settings structure
Split settings: `base.py`, `dev.py`, `staging.py`, `prod.py` + environment variables for secrets. Never hardcode secrets/environment-specific values.

### 19.6 App structure (domain-driven, not just "models.py/views.py" per app)
```
apps/
  orders/
    models.py
    serializers.py
    services.py
    tasks.py
    permissions.py
    urls.py
    tests/
```
Group by **domain/feature**, not by technical layer, once the project grows — easier to navigate/scale a team around.

### 19.7 DRY reusable mixins
```python
class SoftDeleteMixin:
    def perform_destroy(self, instance):
        instance.is_deleted = True
        instance.save(update_fields=["is_deleted"])
```

## 20. TESTING

- **`pytest-django`**: preferred over Django's default `TestCase` runner in most modern teams — cleaner fixtures.
- **`factory_boy`**: generate test model instances without verbose setup.
- **`APIClient` / `APITestCase`**: DRF's test client for hitting endpoints in tests.
```python
class OrderAPITests(APITestCase):
    def test_create_order_requires_auth(self):
        response = self.client.post("/api/v1/orders/", {})
        self.assertEqual(response.status_code, 401)
```
- **Mocking external services** (`unittest.mock.patch`) — never hit real payment gateway/3rd party API in tests.
- **Test DB isolation**: each test wrapped in a transaction, rolled back after (fast, isolated).
- **Factories over fixtures**: fixtures (JSON) are brittle at scale; factories are more maintainable.
- **Contract testing** (Pact) for microservices — ensures consumer/provider API contracts don't silently break.
- **Load/performance testing**: `locust` or `k6` for endpoint throughput/latency under load — essential before scaling claims.

## 22. DEPLOYMENT & SCALING

- **Docker**: containerize app, `Dockerfile` + `docker-compose.yml` for local dev (app+db+redis+celery worker+beat).
- **Gunicorn/Uvicorn workers**: WSGI (Gunicorn) for sync views, ASGI (Uvicorn/Daphne) for async/WebSocket support.
- **Nginx** as reverse proxy: SSL termination, static file serving, load balancing across app instances.
- **CI/CD pipeline**: lint → test → build image → deploy (GitHub Actions/GitLab CI) — never deploy untested code.
- **Blue-Green / Canary deployments**: reduce risk of full rollout — canary sends small % of traffic to new version first.
- **Horizontal Pod Autoscaling (k8s)**: scale app pods based on CPU/memory/custom metrics (queue depth).
- **`django-environ`**: manage settings via environment variables per environment.
- **Zero-downtime migrations**: additive migrations first (add column nullable), backfill, then enforce constraint in a later deploy — never a single migration that locks a huge table in one blocking step.
- **Static/media via S3 + CloudFront (CDN)**, not served by Django directly in production.
- **Feature flags** (django-waffle / LaunchDarkly) — ship code dark, toggle on without redeploy.

## 23. INTERVIEW RAPID-FIRE CHEAT SHEET

- **N+1 fix** → `select_related` (FK/O2O, JOIN) / `prefetch_related` (M2M/reverse FK, separate query).
- **Fast API response** → move work to Celery, cache in Redis, paginate, optimize queries, use indexes.
- **Prevent double charge** → idempotency key + `select_for_update` + `transaction.atomic`.
- **Money type** → always `Decimal`, never `float`.
- **Stateless auth for scale** → JWT (SimpleJWT), short-lived access + rotating refresh token.
- **Multiple services react to one event** → Kafka (event-driven), not Celery.
- **Reliable event publish with DB write** → Transactional Outbox pattern.
- **Prevent cascading failure across services** → Circuit breaker + retries with backoff.
- **Distributed transaction across microservices** → Saga pattern (no 2PC across services).
- **Large table pagination performance** → Cursor pagination over offset.
- **Prevent IDOR** → always scope `get_queryset()` by `request.user`.
- **Prevent abuse** → Throttling (`UserRateThrottle`) + Redis-based custom limiter for precision.
- **DB scaling reads** → Read replicas + `DATABASE_ROUTERS`.
- **DB connection exhaustion at scale** → PgBouncer connection pooling.
- **Zero-downtime schema change** → additive migration → backfill → enforce constraint, split across deploys.
- **Thin views** → business logic in a service layer, not in views/serializers.
- **Webhook trust** → verify HMAC signature before processing.
- **Real-time updates** → WebSockets (Django Channels) over polling.
- **Smallest/fastest payload internal service calls** → gRPC + protobuf over REST/JSON.
